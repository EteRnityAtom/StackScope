# StackScope Firefox Extension

StackScope performs bounded reconnaissance for authorized web application assessments. It can fingerprint common frameworks, crawl same-origin pages and JavaScript, detect in-page module controls, record user-triggered same-origin API traffic, compare eligible GET responses without cookies when explicitly opted in, and show TBHM-aligned manual test ideas.

## Install temporarily in Firefox

1. Extract the ZIP.
2. Open `about:debugging#/runtime/this-firefox`.
3. Choose **Load Temporary Add-on…** and select `manifest.json`.
4. Open an HTTP/HTTPS application you are authorized to assess, click the StackScope toolbar button, and choose a module path or **Whole current origin**.
5. Start the scan and grant Firefox access to that hostname when asked.

This is a Manifest V3 extension for Firefox 128 or newer. Temporary add-ons are removed when Firefox closes. Distribution through addons.mozilla.org requires Mozilla review/signing.

## Scope and JavaScript crawl

- Whole-origin mode is limited to the active tab's exact protocol, hostname, and port. Module mode is limited to the entered origin-relative path and its descendants. `/portal2/` is outside `/portal/`; use Whole current origin for `/`.
- Firefox asks for host access when a scan starts. Page routes must stay inside the selected module path. API URLs found in JavaScript or observed in the open page can use other paths on the active origin because applications commonly serve module data from a shared API prefix. For JavaScript assets on a separate host, enter each exact authorized origin in **Additional authorized JavaScript asset origins**; only script and source-map files are fetched from those hosts. API and page requests remain on the active origin. Redirects are inspected manually and followed only when the destination stays in the applicable page or script scope.
- It reads external script tags, module preloads, observed script resources, bounded inline scripts, and script references found in fetched HTML. It follows static relative imports, discovered JavaScript URLs, and source-map references recursively. Relative API/page strings inside scripts are resolved against the page that loaded the script, while JavaScript imports are resolved against the script URL.
- The initial queue also checks common read-only metadata and API documentation paths such as `robots.txt`, `sitemap.xml`, OpenAPI, Swagger, and Redoc. It follows same-origin URLs from sitemap `<loc>` and robots `Sitemap:` entries only when the selected scope allows them.
- It scans analyzed script text for selected sensitive keyword names and reports only the keyword, source URL, and line number. It never displays or saves matched values. A keyword indicator is not proof of a secret.
- The static crawler uses sequential GET requests with `credentials: include`. By default StackScope does not read cookies or tokens; browser cookie policy may also omit cookies, so treat crawler responses as a browser-session baseline, not proof that the app's bearer-token authentication was applied.
- **Optional bearer-token authentication (opt-in):** when you enable *Use bearer token from page storage for the authenticated crawl*, StackScope reads the active tab's `localStorage`/`sessionStorage`, selects a JWT or token-like value, and sends it as an `Authorization: Bearer` header on the authenticated crawl so token-based apps get a genuinely authenticated baseline. The no-cookie comparison still sends neither cookies nor the token, so enabling this sharpens the authenticated-versus-unauthenticated access-control check. The token value is never displayed or saved — only its storage key (for example `localStorage.access_token`) is recorded in the report. Enable it only for applications you are authorized to test.
- **Possible secrets in JavaScript:** the JS audit tab flags high-signal credential patterns found in analyzed scripts (AWS keys, Google API keys, Stripe/GitHub/Slack tokens, JWTs, private-key blocks, basic-auth-in-URL, and generic secret assignments). Matched values are masked (first and last few characters only) with their source file and line so you can open the file and confirm manually. A match is a lead, not proof.
- **Deep secret scanning (ported from the deepcrawler engine):** in addition to the high-signal patterns, StackScope runs ~780 vendor-specific credential signatures (keyword-gated for speed) plus a Shannon-entropy scan that catches custom/unknown token formats. It filters framework placeholders, implausible values containing code syntax, and base64/hex alphabet constants, and it skips known vendor/library bundles (jQuery, Bootstrap, Swagger UI, etc.) to cut false positives. Every body — HTML, JSON, and JavaScript, plus recovered source-map sources and HTML comments — is scanned, and identical bodies are de-duplicated by content hash. Values are always masked.
- **Endpoint/path extraction** also recognizes bare bundler asset paths (`assets/`, `static/`, `chunks/`, `_next/`, `build/`, `dist/`) and unquoted absolute URLs in comments and concatenations, in addition to quoted absolute and root-relative references. Client-side SPA route tables (React Router, Vue Router, Angular, SvelteKit, Remix, Ember) are extracted so navigable routes that never appear as links or fetch calls are discovered too.
- HTTP Basic/Digest challenges remain under Firefox's control. StackScope does not install a global authentication handler; if Firefox opens an auth prompt during a request, cancel it and assess that route separately.
- The **URLs** tab lists requested HTML page routes separately from API responses. The **Modules** tab lists visible semantic tabs, navigation items, and stepper controls with their full page path; multiple in-page steps can share one URL. For modules that fetch data only after a click, start the click observer and select each control; the observer records the resulting same-origin API calls without changing the page.
- The **Inputs / params** tab inventories named input, select, and textarea fields and shows names (not values) from query strings and supported user-triggered request bodies. It gives manual TBHM-aligned review suggestions, such as object authorization for ID-like names. It never submits field values or test payloads.
- Use **Start click observer** to record same-origin `fetch`, `XMLHttpRequest`, `navigator.sendBeacon`, WebSocket, and EventSource metadata while you click through a module. It records methods, redacted URLs, response status, duration, selected safe response headers, and parameter names from supported request bodies. It briefly associates requests with the last clicked visible tab, step, button, menu item, or link label so same-URL SPA submodules can be distinguished. It never reads input values. Parameter values and response bodies are never stored or shown. It never reads request headers, cookies, or tokens, and never replays non-GET requests. The selected module path applies to the page where you interact; module API calls may use other paths on the same origin.
- StackScope rechecks the active tab before scanning or observing. If the selected tab changes after the popup opens, reopen the popup on the intended target to avoid starting a scan on the wrong tab.
- When Firefox supports dynamic content-script registration, the observer also installs a same-host hook at `document_start` for the next page load. The isolated bridge accepts data only for the original tab, exact origin, and selected module path; Firefox match patterns do not distinguish ports, so the bridge checks the exact origin before storing anything. Stop the observer to remove the temporary registration. The observer keeps at most 1,000 records locally for 24 hours.
- The page can detect or interfere with request hooks, so treat observed traffic as best-effort metadata. Service-worker-owned requests, cross-origin APIs, and calls through browser mechanisms StackScope cannot wrap may not appear. The early hook briefly buffers metadata until Firefox confirms the active scope; out-of-scope pages are rejected and the hook is stopped without saving those events.
- A separate opt-in can issue a same-origin no-cookie GET for eligible query-free observed GET routes. It uses `credentials: omit`, does not follow redirects, skips sensitive and state-changing paths and routes with numeric or UUID path identifiers, records response metadata only, never retains response bodies, and pauses further observer comparisons after HTTP 429 or 503. GET requests can still have side effects. The crawler's anonymous comparison is also GET-only and has a separate bounded route cap.
- App requests using POST, PUT, PATCH, DELETE, or other methods are observed only when the app sends them. StackScope does not replay them without cookies or send guessed request bodies; doing so could change application data. Use authorized test accounts and a safe test environment for method-level authorization checks.
- Resource-timing entries do not include HTTP methods. StackScope lists those fetch/XHR URLs as unrequested candidates instead of guessing GET; method-aware observation is available through the click observer.
- Anonymous comparison is off by default. Its cap is 250 requests by default and 2,000 maximum; it checks discovered API responses and HTML page routes from the scan. Result rows are limited to a login redirect, a 401/403 after a successful browser-session response, or a non-HTML 200 whose selected metadata differs. Identical metadata, HTML shells, unavailable checks, generic redirects, and comparisons without a successful browser-session baseline are counted and hidden as inconclusive. Header matching normalizes media types and ignores cache and infrastructure headers. A differing response is only a manual review lead because response bodies are never examined; raw header values are not shown in the Endpoints or Anon Check views.
- The request cap applies to pages, scripts, and routes together: 1,000 by default and up to 5,000. There is no link or JavaScript recursion-depth cutoff; the URL budget, configurable total deadline, and server rate limits stop the crawl. Each response contributes at most 1.5 MB of text, and total analyzed response text is capped at 8 MB. Inline script capture is also bounded. The report indicates when a cap leaves discovered URLs unrequested.
- The HTTP 200 filter applies to API endpoint responses; scripts and HTML pages are tracked separately. A 200 HTML page is listed under URLs and is never labeled public from status, headers, or size alone. Review API responses and use the click observer for data loaded by in-page modules.
- Known credential/backup files, management dumps, SSRF-triggering routes, likely state-changing GET paths, and routes containing concrete numeric or UUID identifiers are shown as withheld for manual review instead of fetched.

Static parsing cannot discover every runtime-generated route, dynamically assembled import, authenticated workflow, or SPA state. Browser shutdown or closing the popup during an unfinished scan can interrupt that scan.

## Report storage

After a scan, StackScope keeps an unsaved report in this Firefox profile and asks whether to **Save report** or **Discard**. If left unsaved, it is cleared the next time the popup opens after 24 hours. Saved reports remain local until deleted; up to 20 are retained. Reopen the popup to recover an unsaved report or open a saved one. Import a compatible JSON report to keep it in this Firefox profile; imported fields are normalized before display. Exported reports include the scan and matching observed traffic metadata, with URL userinfo and fragments removed, query-string values and credential-like path values redacted. Observed traffic metadata is temporary and expires after 24 hours; clear it from the popup at any time. Response bodies and matched keyword values are not included.

The report contains host/path metadata, browser-session and optional no-cookie response statuses, selected security headers, framework fingerprints, script URLs, keyword locations, and test ideas. JSON export also includes matching-scope observed traffic metadata, clicked control labels, and parameter names; it excludes request/response bodies, input values, and authentication headers. Consider this security assessment data and delete reports when no longer needed.

## TBHM-aligned test ideas

Recommendations are manual review leads, not findings. Depending on detected frameworks, StackScope can suggest checks for XSS, path traversal/LFI, SSTI, CSRF, SQL injection, parameter pollution, SSRF, IDOR, missing function-level access control, mass assignment, deserialization, lazy-loaded route authorization, diagnostic exposure, CORS, cookies/headers, open redirects, and business logic. It does not send exploit payloads, run command-execution attempts, brute-force credentials, enumerate a sensitive-path dictionary, or make CVE claims from framework names alone.

When a framework is fingerprinted, the **Test ideas** tab also shows a manual-review checklist drawn from the TBHM framework cheat sheet: framework-specific recon endpoints (for example Spring Boot `/actuator/*`, Laravel `/telescope` and `/_ignition/execute-solution`, Django `/__debug__/`, Symfony `/_profiler/`, Go `/debug/pprof/`, ColdFusion `/CFIDE/administrator/`), common configuration and secret-leak paths, default dangerous endpoints, template-engine SSTI probes with their confirmation strings, and deserialization/token markers to look for in cookies and bodies. These are leads only. StackScope never requests the listed paths, never sends the SSTI probes, and stores no cookie, token, or body values; the paths are shown prefixed with the active origin so you can review them manually within your authorized scope. Presence of a path in the checklist is not evidence that it exists or is exposed.

No-cookie comparison is opt-in and limited to eligible GET requests. A metadata match or difference is not an authorization finding because response bodies are not inspected. Page-shell-only responses are counted as inconclusive and hidden from actionable result rows; HTML API shells and redirects that cannot be safely classified are excluded from API result rows. The extension does not try alternate identities, bypass authentication, or alter requests with attack payloads. It reads a page-storage bearer token only when you explicitly enable that option, uses it solely to authenticate the crawl, and never displays or stores the token value.

## HTTP method and CORS testing

- **Method probing (opt-in):** *Probe HTTP methods per route* enumerates the server's advertised methods with a safe `OPTIONS` request and compares the `Allow`/`Access-Control-Allow-Methods` header with and without credentials, then actively sends `HEAD` (safe) to read status authenticated and unauthenticated. This surfaces a verb that is reachable without auth — for example `PUT` allowed while `GET` is blocked. Results appear in the **Access / CORS** tab with a per-method verdict.
- **Active state-changing probe (opt-in, dangerous):** a second checkbox additionally sends real `POST`/`PUT`/`PATCH` requests with empty bodies (no crafted payload) to read the response status with and without auth. `DELETE` is never sent automatically, routes whose names look state-changing are skipped, and requests are bounded and paced. Enable it only in an authorized, reversible test environment, because even an empty-body write can change data.
- **CORS test (opt-in):** *Test CORS with a foreign Origin* sends each discovered route a request whose `Origin` header is set, via the `webRequest` API, to the configured value (default `https://www.bing.com`) and reads the server's `Access-Control-Allow-Origin`/`Access-Control-Allow-Credentials` response. A reflected foreign Origin, or a wildcard combined with credentials, is reported as a misconfiguration. Response bodies are not read. This feature needs the `webRequest` and `webRequestBlocking` permissions.
- **Security header audit:** the Access / CORS tab also lists missing or risky response-security headers (CSP, HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, wildcard CORS, version disclosure) observed on the primary response. These are review leads, not confirmed findings. Run it only when written bug-bounty authorization explicitly covers the exact hostname, page paths, APIs, and any additional JavaScript asset origins; other hosts remain outside this scan.
